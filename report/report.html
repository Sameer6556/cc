Overview, architecture and how to read this report

The teacher (phi3.5, 3.8 B parameters, served by Ollama) labels the 3,000 pool commands with a four-key JSON frame; clean.py filters the replies into a training set; Pythia-70M is fine-tuned on the first 1,500 records (sequence-level distillation); the student is served by a FastAPI service behind a Traefik Ingress with an HPA. All long-running experiments were executed with the repository's own Makefile targets and scripts on GitHub-hosted runners (Ubuntu 24.04, 4 vCPU, 16 GiB RAM), from a fresh clone each time, by the workflows label, train and experiments, which commit their evidence to results/; the same commands run unchanged on a laptop (see README).

Task 1. Object storage and parallel teacher labelling

Architecture. The cluster is a single k3s node; Traefik is published on host port 8080 and the S3 port of SeaweedFS on 127.0.0.1:30333 only. SeaweedFS 4.47 runs as one weed server -s3 Pod in namespace data on a 5 GiB volume. S3 credentials are generated at deploy time (scripts/secrets.sh) straight into Kubernetes Secrets: an admin identity for the pipeline and a read-only identity limited to the models bucket for the service (checked: GET/LIST on models allowed; GET on datasets, PUT and DELETE denied). make up creates the buckets datasets and models and uploads commands_pool.jsonl. The teacher runs inside the cluster (Ollama 0.40.9, namespace pipeline, phi3.5 pulled by an init container) with temperature 0 and seed 42 hard-coded in worker/teacher.py, plus num_predict 128 and num_ctx 2048.

Prompt (prompts/teacher_prompt.txt). It restates the four keys, gives a one-line definition per intent, the three slot rules, and two conventions of the data (drop "next"; parts of the day and words such as "near me" are not slots), followed by 13 examples I wrote. None of the 13 commands occurs in the pool or the validation set (checked by script), so no hand-made label can leak into the training data.

Sharding. Worker k of K owns the commands whose 0-based line number n satisfies n mod K = k. The workers are one Kubernetes Indexed Job with completions = parallelism = 2; each Pod receives its completion index through the downward API as SHARD_INDEX, and SHARD_COUNT=2. The assignment is a pure function of the line number, so the shards are disjoint and together cover every line without any coordination, locking or shared state; each worker writes only its own object datasets/teacher/shard-k.jsonl, so there are no write conflicts. Round-robin (rather than contiguous blocks) keeps the shards balanced even if command length drifts through the file. A worker uploads its partial object every 25 replies and, when restarted, skips the ids already present, so a Pod failure costs at most 25 teacher calls. Ollama decodes the two workers' requests together (OLLAMA_NUM_PARALLEL=2). The trade-off of a static split is that a slow worker cannot hand work to a fast one.

Cleaning decisions A. A reply is parsed after trimming surrounding whitespace (as score.py does); a repeated key counts as (b); NaN is invalid JSON; rule (d) compares whole words, case- and space-insensitively, so "mon" does not match "monday" and an empty string never matches. Rules (a)-(d) are applied first, then duplicates among the survivors. Each kept line stores the exact teacher_raw reply and a target: the same object re-serialised with the key order intent, date, time, place (values unchanged; PENDING of PENDING kept replies were already byte-identical to it). Limitations / improvements: rule (d) checks form, not meaning, so a wrong-but-present span is kept; with only 4 vCPU the teacher is compute-bound, so more workers would not help; a work queue (or a Job per chunk) would remove the static-split imbalance, and a second teacher pass on rejected commands could recover data.

What changed. The untrained model does not produce the frame at all; after distillation the student emits a schema-valid frame for almost every command, and its errors are concentrated in the slots, where it has to copy an exact span. Because the student is trained only on the teacher's replies, the teacher's full-frame accuracy is effectively its ceiling, and the teacher's systematic deviations from the SLURP conventions are inherited.

Sequence-level vs logit-based distillation

(a) Sequence-level KD (Kim and Rush, 2016), used here, trains the student with ordinary cross-entropy on the teacher's generated output sequence: the teacher's (approximate) mode, decoded greedily, is treated as the hard target ŷ, and the student maximises log pS(ŷ | x). (b) Logit-based (word-level) KD (Hinton et al., 2015) instead trains on the teacher's full next-token probability distribution at every position, minimising KL(pT(· | x, y<t) || pS(· | x, y<t)), usually with a temperature, so the student also learns how the teacher spreads probability over the alternatives (the "dark knowledge"). (c) It is not possible here for two independent reasons: Ollama's API returns the generated text, not the per-position distribution over the whole vocabulary; and even with logits, phi3.5 (Llama-style SentencePiece, 32,064 tokens) and Pythia (GPT-NeoX BPE, 50,304 tokens) tokenise text differently, so their distributions are over different vocabularies and different token boundaries and cannot be compared position by position without an alignment method. (d) Limitation of what I did: the student sees one hard answer per command, so it copies the teacher's mistakes with full confidence (for example its slot boundaries, which differ from the SLURP labels used for scoring), and it gets no signal about which commands the teacher was unsure of; the filter in Task 1 removes malformed replies but cannot remove fluent, wrong ones.

Task 3. The inference service in a container

Implementation. FastAPI (service/app.py), port 8000. POST /parse runs greedy generation, validates the output against schema.json with jsonschema (exactly the four keys, one of the eight intents, string-or-null slots, NaN rejected) and returns either HTTP 200 with only the object or HTTP 500 {"error": "invalid_model_output"}; both carry X-Model-Version and X-Served-By (the Pod name from the downward API). /healthz answers 200 while the process lives; /readyz is 503 until a background thread has downloaded every object under MODEL_URI from S3_ENDPOINT, verified each file against model.sha256, loaded the model and run one warm-up generation. Configuration comes from MODEL_URI, MODEL_VERSION, S3_ENDPOINT and MAX_NEW_TOKENS; credentials only from the Secret; FAULT_INJECT=1 replaces the output with not json before validation. One generation runs at a time per Pod (a lock), and torch uses as many threads as the container's CPU limit (read from the cgroup). The image (service/Dockerfile) installs the CPU-only torch wheel, then every other package from a fully pinned lock with --no-deps and pip check; it runs as a non-root user and contains no weights.

Limitations. A The cluster is one k3s node in one container on one machine: the experiments show recovery from a lost Pod, not from a lost node, disk or machine; there is no fault tolerance across machines, and SeaweedFS is a single replica on a single volume. The HPA reacts to metrics-server samples (15 s) plus a stabilisation window, so it lags short bursts; and the replica count is capped at 2 by the assignment. Improvements: 3+ nodes (k3d agents) with pod anti-affinity, a PodDisruptionBudget, SeaweedFS replication, a startup probe instead of a long liveness delay, and an HPA on request latency rather than CPU.

Why stateless rules need reply rules, and why order matters. A NACL keeps no connection state: every packet, including a reply, is evaluated on its own. When a client opens a connection to the load balancer on 443, the answer leaves the subnet towards the client's ephemeral port (1024-65535); without outbound rule 110 every response would be dropped. Likewise the load balancer's request to the app goes out on TCP 8000, but the app's answer arrives on one of the load balancer's ephemeral ports and needs inbound rule 130 (a stateful security group would allow both automatically). Rules are checked from the lowest number and the first match wins. A packet from 198.51.100.9 to port 443 matches both the deny and the "443 from anywhere" allow, so the deny only works if its number is lower than the allow it must override: renumbering it from 50 to 140 lets that packet in (results/network/nacl_wrong_order_check.txt, 5 / 6). Limitation: a stateless NACL cannot tell a reply from a new connection, so outbound rule 110 also permits new connections to any high port.
